# FSM_UserIO 0.1.0-alpha.2 — Release Readiness and Remaining Work

**Next-release target:** `0.1.0-alpha.2` (provisional; not yet a project-version change or publication decision)  
**Prior package target:** `0.1.0-alpha.1`  
**Publication status:** not confirmed by the repository evidence in this checklist; verify NuGet independently before describing any version as published.  
**Candidate source:** `development`; this checklist must be revalidated against the eventual release commit.  
**Purpose:** define the next release's minimum stable semantic boundary, required proof, and remaining work without turning every conceptual interaction into a new public API.

> This is a release gate, not a statement that the candidate is already ready or published. A passing run applies only to the exact commit it tested.

## Release rule

The next release should make the small implemented contract and the larger domain boundary easier to understand without inventing APIs for concepts that lack a demonstrated consumer.

The current core contract is:

```csharp
SemanticIntent(string Name, ulong? ProtocolId = null)
```

The next release should preserve that boundedness unless a concrete, reviewed defect proves a code change necessary. Documentation completion is not a reason by itself to expand the public API.

- Keep FSM_UserIO platform-neutral and free of runtime package dependencies.
- Keep `Name` application-owned and preserve a valid nonblank value exactly as supplied.
- Treat `ProtocolId` as an optional value slot only; UserIO does not allocate IDs, own a vocabulary, authenticate producers, authorize an action, or execute an intent.
- Keep capability, observation, expression/proposal, intent, authority, and execution distinct.
- Do not publish until every P0 gate is satisfied and the owner explicitly authorizes publication.

## Priority legend

- **P0 — release blocker:** required before the next alpha can ship.
- **P1 — readiness decision:** resolve or explicitly record why it is deferred before release review.
- **P2 — follow-up:** valuable future work, not an implied promise for alpha.2.

- [ ] Record the exact candidate commit SHA and the CI run that validates it.
- [ ] Confirm README, theory, architecture, roadmap, API contracts, package metadata, release notes, and the readiness document describe the same implemented contract.

## 1. Lock the implemented semantic contract

### P0

- [ ] Confirm the only shipped core domain artifact remains `SemanticIntent` unless a separately reviewed implementation change is approved.
- [ ] Confirm a null, empty, or whitespace-only name is rejected with the documented exception behavior.
- [ ] Confirm a valid name is preserved exactly; do not silently trim or normalize application-owned meaning.
- [ ] Confirm `ProtocolId` is nullable and optional, and that the core neither allocates nor resolves protocol identities.
- [ ] Confirm value equality is documented and tested.
- [ ] Ensure the API contract document describes exact behavior and does not claim untested behavior.
- [ ] Keep public XML documentation coherent, nullable analysis clean, and warnings treated as errors.
- [ ] Preserve the zero-runtime-dependency and platform-neutral core boundary.

Current test traceability is centered on `tests/FSM_UserIO.Tests/SemanticIntentTests.cs`, including name preservation, optional protocol identity, blank-name rejection, and value semantics. Verify the exact source and test names on the release commit; this document does not replace that inspection.

## 2. Close the domain boundary without speculative API

### P0

- [ ] Keep the domain roadmap explicit about what is implemented, conceptual, deferred, and owned by another package or host.
- [ ] Confirm ownership remains clear:
  - **FSM_UserIO:** semantic intent carrier.
  - **ProtocolAi:** deterministic vocabulary identity and protocol symbol mapping.
  - **GrammarAi:** grammar and structure.
  - **GUI:** presentation and semantic GUI tree.
  - **Adapters/platforms:** native event and device mapping.
  - **Host/application:** meaning, validation, authorization, policy, and execution.
  - **FSM_COS:** runtime composition.
  - **Transport/persistence:** delivery, retries, ordering, replay, and storage when needed.
- [ ] Verify dependency direction: adapters may depend on UserIO; UserIO must not depend upward on GUI, ProtocolAi, GrammarAi, FSM_COS, Unity, WPF, Blazor, or a game engine.
- [ ] Preserve the distinction: capability is not authority; an intent is not execution; a protocol identity is not authentication.
- [ ] Ensure diagrams use a clear visual distinction between the implemented `SemanticIntent` and conceptual or deferred areas.
- [ ] Confirm the domain completion criteria do not require a public type for every listed domain concept.

The following are **not** required for alpha.2 merely for completeness: universal actor hierarchies, capability descriptors or negotiation, source-observation and expression/proposal types, payload/session/feedback abstractions, device-specific APIs, authentication, authorization, execution, transport guarantees, or a universal capability ontology.

## 3. Prove a consumer can use the contract

### P0

- [ ] Build the integration walkthrough against the published Alpha 1 package and verify its output, or upgrade it to the approved candidate package only after that package exists.
- [ ] Keep the source adapter and host policy clearly labeled as local example code, not public UserIO APIs.
- [ ] Demonstrate that a source-specific event can be mapped to an application-owned `SemanticIntent`.
- [ ] Demonstrate that the host can accept or reject that intent without UserIO authorizing or executing it.
- [ ] Seek one real downstream consumer or adapter integration as release evidence. If none exists yet, record this gap explicitly and decide whether it blocks the next alpha; do not present a documentation-only walkthrough as cross-repository integration proof.
- [ ] Confirm the example compiles from a clean checkout and has a clear expected output.

- [ ] Theory and Architecture distinguish the intended semantic-interaction domain from the single implemented core contract.

- [ ] Any remaining consumer, test, or contract gap is listed as open rather than implied to be complete.

## 6. Deferred concepts — not alpha.2 promises

These remain design questions unless a real consumer and a separately approved contract establish otherwise:

- Source-neutral observation and expression/proposal models.
- Structured interaction payloads, sessions, and feedback.
- Capability discovery and negotiation.
- Adapter conformance suite.
- Provenance/trust, replay, deduplication, ordering, and idempotency guarantees.
- Device, UI framework, network transport, or runtime-composition APIs.
- Authentication, authorization, policy, and domain execution.

A proposed addition must name its consumer, semantic owner, invariant, test strategy, and evolution/compatibility behavior before it becomes a release requirement.

## 7. Follow-up readiness work

### P1 — resolve or explicitly defer

- [ ] Decide whether a real downstream integration is a strict release blocker for alpha.2 or an explicit alpha limitation.
- [ ] Verify constructor edge cases directly against source and tests, including null and whitespace input; do not claim a test exists unless it does.
- [ ] Verify the packed package includes the documentation promised by the project file.
- [ ] Review test coverage for meaningful contract invariants rather than chasing a percentage.
- [ ] Confirm that the domain completion criteria and roadmap distinguish package completion from completion of the entire semantic-interaction vision.
- [ ] Ensure the next release notes state exactly what changed from Alpha 1 and do not imply deferred APIs were implemented.

### P2 — future work, not a release promise

- A source/adapter conformance suite after shared adapter contracts exist.
- A second consumer demonstrating that the semantic boundary remains unchanged across unrelated source modalities.
- Additional domain types only when concrete integration evidence proves a shared contract is necessary.

## 8. Publication gate

- [ ] Approve the next version number and release scope.
- [ ] Confirm the release commit, package version, package contents, and all P0 gates.
- [ ] Resolve or explicitly accept the P1 readiness decisions.
- [ ] Obtain explicit owner approval for publication.
- [ ] Deliberately dispatch the build workflow on `development` with `publish: true`; ordinary pushes and pull requests must not publish.
- [ ] Verify the publish job succeeded and the exact package version is visible on NuGet.
- [ ] Record version, commit SHA, workflow run, and package URL.
- [ ] Leave no accidental publication authorization in place after the release.

## Exit condition

The next alpha is ready when the smallest semantic boundary is exact, the wider domain and ownership map are explicit, the consumer path and package artifact are verified, documentation matches implementation, and publication is separately authorized. If a requirement is not evidenced, keep it open.
